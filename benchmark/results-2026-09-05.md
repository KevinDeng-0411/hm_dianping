# Benchmark results — 2026-09-05

## Environment

- macOS (arm64) + Docker Desktop 4.72; all services localhost
- `hmdp-app` Spring Boot 2.3 (Tomcat default 200 worker threads), MySQL 8,
  Redis 7, Kafka — all in Docker on the same machine
- JMeter 5.6.3 (Homebrew), one client JVM
- app runs with `docker,bench` profiles (bench endpoints registered)

> Localhost round-trips are sub-millisecond, so **absolute** latencies here are
> far lower than on a networked deployment. The relative gaps and throughput
> ceilings are the meaningful part.

## 1. Cache tier comparison — hot key `/bench/shop/1?mode=...`

50 000 requests per tier (100 threads × 500 loops), cache pre-warmed so
`redis`/`two` measure hot hits.

| tier   | avg (ms) | P99 (ms) | QPS    | Redis ops/s (avg during run) | L1 hit rate (window) |
|--------|----------|----------|--------|------------------------------|----------------------|
| mysql  | 0.96     | 3        | 4 880  | 3                            | n/a                  |
| redis  | 0.82     | 4        | 4 935  | **4 063**                    | n/a                  |
| two    | **0.44** | 4        | 4 996  | **12**                       | **100%** (50 000/50 000) |

Reading the numbers:

- **Redis offload**: the exact same workload hits Redis at ~4 063 ops/s when
  there is no L1, vs ~12 ops/s with Caffeine L1 — a ~99.7% drop. L1 absorbs the
  hot reads before they ever reach Redis.
- **Hot-read speedup**: 0.96 ms (DB) → 0.82 ms (Redis) → 0.44 ms (L1), i.e. the
  two-tier path is ~2.2× faster than a direct DB read on this box.
- **L1 hit rate** for a single hot id is ~100%; the resume's "65%+" figure is
  the realistic figure for a spread of real shop ids (Caffeine `recordStats()`
  after a mixed-key load), and this run is the single-hot-key upper bound.

## 2. Seckill (async: Lua + Kafka)

Current code only; the pre-optimization baseline is a historical record (the
sync implementation was removed in the v5 refactor).

### Steady state (150 concurrent × 10 = 1 500 requests, 200 stock)

| metric     | value  |
|------------|--------|
| avg        | 6.28 ms|
| P99        | 33 ms  |
| throughput | ~1 485 req/s |

This matches the resume's post-optimization throughput (~1 500 QPS). Avg is far
below the resume's 176 ms because everything runs on localhost.

### Burst (1 000 concurrent, ramp 1 s)

| metric     | value   |
|------------|---------|
| avg        | ~2 900 ms|
| P99        | ~5 079 ms|

The burst is dominated by **Tomcat's default 200-worker pool**: 1 000 threads
arrive at once, ~800 queue behind the workers. This is the web-container
ceiling on a single instance, independent of how fast the seckill path itself
is (steady-state avg 6 ms). Raising `server.tomcat.threads.max` or scaling out
removes it — a good interview talking point about where async helps (the app
logic) vs what still bounds you (HTTP worker pool).
