# 压测结果 —— 2026-09-05

## 环境

- macOS (arm64) + Docker Desktop 4.72；全部服务在本机
- `hmdp-app`：Spring Boot 2.3（Tomcat 默认 200 worker 线程）、MySQL 8、
  Redis 7、Kafka，全部跑在 Docker（同一台机器）
- JMeter 5.6.3（Homebrew），单客户端 JVM
- app 以 `docker,bench` profile 启动（注册了 `/bench/*` 压测端点）

> 本机回环延迟是亚毫秒级，所以这里的**绝对延迟**比真实网络部署低得多，
> 有参考价值的是**相对差距**和**吞吐上界**。

## 一、缓存三档对比 —— 热点 key `/bench/shop/1?mode=...`

每档 5 万请求（100 线程 × 500 次），压测前先预热，保证 `redis`/`two` 两档
测的是"热缓存命中"。

| 档 | avg (ms) | P99 (ms) | QPS | Redis ops/s（运行期均值） | L1 命中率（窗口） |
|---|---|---|---|---|---|
| mysql（纯 DB） | 0.96 | 3 | 4 880 | 3 | — |
| redis（无 L1） | 0.82 | 4 | 4 935 | **4 063** | — |
| two（二级） | **0.44** | 4 | 4 996 | **12** | **100%**（50 000/50 000） |

怎么解读：

- **Redis 负载下降**：同一负载下，没有 L1 时 Redis 约 4 063 ops/s；加了
  Caffeine L1 只剩约 12 ops/s，**下降约 99.7%**。热点读在到达 Redis 之前
  就被本地缓存吸收了。
- **热点读加速**：0.96ms（DB）→ 0.82ms（Redis）→ 0.44ms（L1），二级缓存
  路径比直查 DB 快约 **2.2 倍**（本机）。
- **L1 命中率**：单热点 id 接近 100%。简历上"65%+"是真实多店铺负载下的
  合理值（压完 `Caffeine.recordStats()` 读出），本次单 key 是其上限。

## 二、秒杀异步（Lua + Kafka）

只有当前代码版本；优化前基线是历史记录（同步实现已在 v5 重构中删除）。

### 稳态（150 并发 × 10 = 1500 请求，200 库存）

| 指标 | 数值 |
|---|---|
| avg | 6.28 ms |
| P99 | 33 ms |
| 吞吐 | ~1485 req/s |

吞吐与简历优化后的 ~1500 QPS 吻合；avg 远低于简历的 176ms，因为全部在本机
回环跑。

### 洪峰（1000 并发，ramp 1s）

| 指标 | 200 worker（基线） | 1000 worker + accept 1000（放大调参） |
|---|---|---|
| avg | ~1076 ms | ~3063 ms |
| P99 | ~2108 ms | ~5045 ms |
| connect 均值 | ~390 ms | ~1376 ms |
| 新建连接 | 997 / 1000 | 998 / 1000 |

**归因实测**（把 JMeter CSV 的 `Connect` / `Latency` / `elapsed` 拆开）：

- 1000 并发下 **997/1000 是新建 TCP 连接**（每个用户只发 1 次请求，keep-alive 无法复用）。
- `elapsed ≈ Latency`，而 `Connect` 平均 390ms（基线）、p95 1.2s、峰值 1.6s——
  时间基本花在"到首字节之前的 TCP 建连 + 连接队列排队"上。
- 把 `server.tomcat.threads.max` 与 `acceptCount` 放大到 1000 后，延迟**没有下降反而升高**
  （avg 1076 → 3063ms，connect 390 → 1376ms）：瞬时 1000 个新连接 + 1000 线程并行，
  放大了容器网络栈 / 内核连接队列与机器资源的争抢。

修正后的结论：洪峰延迟的主因是**单实例容器网络栈在瞬时海量新 TCP 连接下的建连
开销与内核 accept 排队（连接层）**，而不是 Tomcat worker 池、更不是业务链路
（稳态连接复用下 avg 仅 6ms）。这也解释了为什么"放大 worker"无效——连接建立
在应用代码到达之前，就已经在内核 / 容器转发层排队。正确解法是**横向扩容分摊
连接、边缘网关在连接 / IP 层面限流，或用 CDN 抗连接洪水**。

> 这比"worker 池瓶颈"更接近真相：业务层的异步优化解决的是 DB 写入，而一次性
> 新连接的建立成本，是单机压测最容易误归因的坑。
