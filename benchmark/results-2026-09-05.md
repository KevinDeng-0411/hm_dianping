# 压测结果 —— 2026-09-05

## 环境

- macOS (arm64) + Docker Desktop 4.72；全部服务在本机
- `hmdp-app`：Spring Boot 2.3（Tomcat 默认 200 worker 线程）、MySQL 8、
  Redis 7、Kafka，全部跑在 Docker（同一台机器）
- JMeter 5.6.3（Homebrew），单客户端 JVM
- app 以 `docker,bench` profile 启动（注册了 `/bench/*` 压测端点）

> 本机回环延迟是亚毫秒级，所以这里的**绝对延迟**比真实网络部署低得多，
> 有参考价值的是**相对差距**和**吞吐上界**。

## 一、缓存三档对比 —— 热点 key `/bench/shop/1?mode=...`

每档 5 万请求（100 线程 × 500 次），压测前先预热，保证 `redis`/`two` 两档
测的是"热缓存命中"。

| 档 | avg (ms) | P99 (ms) | QPS | Redis ops/s（运行期均值） | L1 命中率（窗口） |
|---|---|---|---|---|---|
| mysql（纯 DB） | 0.96 | 3 | 4 880 | 3 | — |
| redis（无 L1） | 0.82 | 4 | 4 935 | **4 063** | — |
| two（二级） | **0.44** | 4 | 4 996 | **12** | **100%**（50 000/50 000） |

怎么解读：

- **Redis 负载下降**：同一负载下，没有 L1 时 Redis 约 4 063 ops/s；加了
  Caffeine L1 只剩约 12 ops/s，**下降约 99.7%**。热点读在到达 Redis 之前
  就被本地缓存吸收了。
- **热点读加速**：0.96ms（DB）→ 0.82ms（Redis）→ 0.44ms（L1），二级缓存
  路径比直查 DB 快约 **2.2 倍**（本机）。
- **L1 命中率**：单热点 id 接近 100%。简历上"65%+"是真实多店铺负载下的
  合理值（压完 `Caffeine.recordStats()` 读出），本次单 key 是其上限。

## 二、秒杀异步（Lua + Kafka）

只有当前代码版本；优化前基线是历史记录（同步实现已在 v5 重构中删除）。

> ⚠️ 数据修正：早期「稳态 1485 QPS / avg 6.28ms」来自 JMeter CSV `shareMode.thread`
> 的 token 打散 bug（每线程从文件头读，1000 线程全取到最前几个 token，被
> `@RateLimit` 大量拦截、成功样本失真）。改为 `shareMode.all` 重测，数字以下表为准。

### 稳态（200 并发 × 5 = 1000 请求，200 库存，`shareMode.all`）

| 指标 | 数值 |
|---|---|
| avg | 9.0 ms |
| P99 | 58 ms |
| 吞吐 | ~1050 req/s |
| Redis 判成功 | 200 |
| DB 落库 | 200（与 Redis 完全一致 → 一条不丢） |

与简历优化后 ~1500 QPS 同量级、方向一致；avg 更低因全部本机回环。

### 消息不丢失 + 堆积（本轮落地实测）

落地（配置 `application-docker.yml` + 代码 `SeckillOrderConsumer`）：
- 生产者 `acks=all` + `enable-idempotence=true` + `retries=3`；发送 `addCallback` 失败留痕
- 消费者 `enable-auto-commit=false` + `ack-mode=batch`：处理成功才提交 offset，
  崩溃变"重复消费"、由唯一键幂等兜底（取"宁可重复、不丢"）
- 消费 `concurrency=3` 对齐主题 3 分区 → 洪峰积压并行消化

验证：稳态与洪峰两轮 **Redis 判成功 = DB 落库 = 200**，判成功的订单一条不丢；
洪峰结束后数秒内 200 单全部异步落库（并发消费、积压清空快）。

### 洪峰（1000 并发，ramp 1s）

干净洪峰（1000 并发，ramp 1s，`shareMode.all`）：

| 指标 | 数值 |
|---|---|
| avg | ~1112 ms |
| P99 | ~1912 ms |
| 新建连接 | 997 / 1000（keep-alive 无法复用） |

延迟秒级的归因仍是**连接层**（拆 CSV：`Connect` 平均 ~390ms、`elapsed≈Latency`，
时间耗在 TCP 建连与连接队列排队，业务链路毫秒级）。把 `threads.max`/`acceptCount`
放大到 1000 实测反而更差（avg 3063ms）——管道瓶颈在连接层而非 worker 池，
与是否正确打散 token 无关。正确解法是横向扩容分摊连接、边缘网关在连接/IP 层
限流、或用 CDN 抗连接洪水。

> 业务层的异步优化解决的是 DB 写入，而一次性新连接的建立成本，是单机压测最
> 容易误归因的坑。
