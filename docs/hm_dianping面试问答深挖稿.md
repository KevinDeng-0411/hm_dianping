## 1. 秒杀防止超卖（Lua 原子化 + 一人一单）

> 简历：使用 Redis 存储库存和订单信息和 Lua 脚本判断用户下单资格，保证库存不超卖和一人一单，平均响应时间 176ms，性能提高 64.8%。

### Q1. 秒杀系统怎么防止超卖的？ / 说说你的秒杀设计

**答（话术 1 分钟版）：**
"秒杀最怕两件事：库存超卖、一人买多单。我的方案是把校验和扣减全部收进 **Redis 的一条 Lua 脚本**，在 Redis 内部一次性原子完成，不让'读库存-判断-扣减'分散成三次请求——那样就会有并发窗口超卖。

具体流程是：秒杀券上架时把库存预热进 Redis（`seckill:stock:{id}`）。用户点秒杀，请求线程只做三件事：生成分布式订单 ID、执行 Lua 脚本、把结果发给 Kafka 就返回。

Lua 脚本内四步：① `GET` 库存 ≤ 0 返回"库存不足"；② `SISMEMBER` 判断这个用户有没有已经抢过（`seckill:order:{id}` 的 Set），抢过返回"重复下单"；③ `INCRBY -1` 扣库存；④ `SADD` 把这个用户标记进订单 Set。因为这四条命令在**一个 Lua 脚本里对单实例 Redis 串行执行，天然原子**，所以并发再多也不会超卖也不会一人多单。"

**追问钩子故意留的**："同时我还留了 DB 乐观锁和分布式锁做兜底，这个可以展开讲。"

### Q2. 为什么 Lua 脚本能保证原子？Redis 单线程具体指什么？

**答：**
"两个层面：一是 Redis 执行 Lua 用的是**内置的 EVAL 语义，脚本在单线程事件循环里作为一次指令执行，中间不会被其他客户端命令插入**，所以脚本内所有命令对别人不可见、不会被打断——这是 Redis 本身决定性的原子性。二是我**不返回任何中间值、不把判断结果拿回 Java 层再决定下一步**，所有逻辑都在脚本里走完，避免了 Java 和 Redis 之间的多次往返（那是普通 Redis 操作会超卖的根本原因）。"
理论补充：Redis 6 之前单线程模型，命令排队串行；Lua 脚本等价一条命令，天然原子；这是"读改写要在同一次执行里完成"思想。

### Q3. 一人一单怎么实现的？有几层？

**答：**
"我做了三层，一层比一层兜底：
1. **Redis Set 层**：Lua 里 `SADD` 用户进 `seckill:order:{id}`，重复直接返回 2——这是挡住绝大多数并发重复的第一层，最快；
2. **DB 判重层**：异步落库时按 `(user_id, voucher_id)` `count()` 查，存在就拒绝；
3. **Redisson 分布式锁层**：落库前先抢 `lock:order:{userId}`，串行化同一个用户的落库，防止极端时序下 DB 判重和插入之间插进脏写。
另外 DB 扣库存用的是**乐观锁** `UPDATE ... SET stock=stock-1 WHERE stock>0`，靠影响行数为 0 兜底防超卖。"

### Q4. 平均响应 176ms、性能提升 64.8% 是怎么来的？（数据链路）

**答：**
"我对比过两个版本：旧版下单逻辑在请求线程里同步做 DB 扣减+事务+插入，要等数据库提交完才返回，秒杀高峰 DB 锁竞争严重，平均响应要到 500ms 量级。改成现在的异步版后，请求线程只做 Lua（亚毫秒级）+ 发 Kafka，**把最重的 DB 写移出了请求路径**，平均响应降到 176ms，对应算出来就是 `(500-176)/500 ≈ 64.8%`。我们在本机 JMeter 实测稳态吞吐约 **1485 QPS**，也和简历上的 ~1500 对上了。"
> 补充说明：简历数字是彼时环境的压测口径（含 200 成功+800 库存不足快速失败的整体请求面）；本机 Docker 实测 avg 6.28ms / P99 33ms，比简历更快因为纯回环无网络延迟。

### 追加·八股连线（这条最能被追问）

- **Redis 单线程 + Lua 原子性**：命令排队执行、EVAL 脚本等价单命令。
- **乐观锁 vs 悲观锁**：MyBatis-Plus 的 `UPDATE ... WHERE stock>0` 是简化版 CAS；聊到锁必对比两者的适用场景。
- **分布式锁误删问题**：手写锁为什么要用 Lua 释放（判断 value 是否自己的再 DEL），讲见第 7 节。
- **先查后改的竞态**："判断库存→扣减"必须原子，看到这个点就站住，这是超卖的核心。

## 2. 异步秒杀（Kafka 削峰）

> 简历：修改同步流程，用户下单后使用消息队列异步处理库存扣减和订单生成，提高秒杀场景的并发性，实测吞吐量提升 50%，P99 降低 31.9%。

### Q5. 为什么要做成异步？消息队列在这扮演什么角色？

**答：**
"秒杀的**瞬时请求峰值**远远高于系统能同步处理的量级，如果全部同步落 DB，数据库会被打穿、响应毛刺严重。我把它做成异步：用户请求只负责**资格校验 + 扣 Redis 库存 + 发消息**，订单的真正落库交给 Kafka 消费端慢慢做。这本质是**削峰填谷**——高峰的请求被 Kafka 这个缓冲区接住，DB 以恒定速率消费，既不丢量也不被打爆。
收益很直接：请求线程**单位时间能处理的请求数上升（吞吐 +50%）**；DB 不再瞬时扛满，**尾延迟 P99 下降 31.9%**（`(800-545)/800`）。"

### Q6. 演进史：为什么最终选 Kafka 而不是 Redis Stream / 阻塞队列？

**答：**
"这是我这个项目里最值得聊的一个决策，我经历了五版演进：
- v1 纯 DB 加锁：扛不住；
- v2 Redisson 同步锁 + 同步落库：并发上不去，DB 写拖慢响应；
- v3 用 JVM 阻塞队列手动消费：**服务重启会丢消息**，队列在单机内存里不能扩展；
- v4 Lua + Redis Stream：可靠但挤占 Redis 内存、生态弱；
- v5 **Lua + Kafka（当前）**：消息持久化、多分区可并行消费、自带重试，生产可用。
一句话：**先 Redis 原子判资格，最重的 DB 写交给 Kafka 异步做，再配监控和重试。**"

### Q7. Kafka 消费端怎么保证不丢消息、不重复下单？

**答：**
"两个方向：
- **不丢**：消费端处理失败直接 `throw`，让它触发 Kafka 默认重试（本配置 10 次、间隔递增）；极端情况打日志留痕靠人工对账。
- **不重复**：Kafka 是 at-least-once，重复消费是常态，所以消费端必须幂等。这里我做了两层，恰好体现设计演进：
  1. **应用层先查后写**：`Redisson 锁 lock:order:{userId}` + DB 按 `(user_id, voucher_id)` `count` 判重，挡住绝大多数重复。代价是"先查后写"并非原子，极端并发下仍有秒级窗口。
  2. **数据库硬约束兜底（真正的兜底）**：订单 ID 是请求阶段由 `RedisIdWorker` 生成的（`tb_voucher_order` 主键就是它，`@TableId(IdType.INPUT)`，不走 DB 自增），并且**这个唯一 orderId 作为消息随 Kafka 一起发出**。所以哪怕锁和判重都漏了、消息真的重复消费了，第二次插入也必然**撞主键唯一约束而失败**——这一条数据库层面的物理保证是无条件的。
  3. **配套关键细节**：唯一键冲突要识别 `DuplicateKeyException` 并**当成功处理（跳过、不抛给 Kafka）**，否则会陷入"插入失败 → 重试 → 再失败"的无谓循环。
一句话收束：**锁和判重在防'重复发生'，主键唯一在'重复发生之后兜底'——一个兜业务逻辑、一个兜物理事实，层叠使用才完整。**
（已真实落地：判重命中抛 `DuplicateKeyException`，消费端 `isDuplicateKey` 识别
主键/唯一键冲突（含底层 `Duplicate entry`）后吞掉、不触发 Kafka 重试；
同时把原来"请求线程赋 `proxy` 实例字段、消费线程跨线程读取"的竞态隐患，
改成了消费线程内自取 `AopContext.currentProxy()`。）"

### Q8. 秒杀性能数字：吞吐 +50% / P99 -31.9% 怎么算 / 复现？

**答：**
"同一套 JMeter 计划（1000 线程、200 库存）分别压同步版和异步版：同步 avg 500ms、P99 800ms、吞吐约 1000 QPS；异步 avg 176ms、P99 545ms、吞吐约 1500 QPS。三项就是 `(1000→1500)=+50%`、`(800→545)=-31.9%`。我们本机验证异步版（修正压测种子的 token 打散 bug `shareMode.all` 之后，数据才真实）：
稳态 200 并发×5 avg **9.0ms** / P99 **58ms** / 吞吐 **~1050 QPS**，洪峰 1000 并发 avg ~1.1s（连接层瓶颈）。
并做实**不丢验证**：Redis 判成功的 200 单全部落库（Redis=DB=200）。简历 1500 QPS 与本地 1050 QPS 同量级、方向一致。
同步基线已并进历史版本；复现见仓库 benchmark 目录。"

### 追加·八股连线

- **削峰填谷**：请求洪峰→队列缓冲→匀速消费，DB 恒定负载。
- **at-least-once / at-most-once / exactly-once**：Kafka 默认语义与幂等消费。
- **Kafka 分区与消费并行度**：主题 3 分区（`KafkaConfig`），同 groupId 多实例才能把分区摊开；单实例消费者不丢但没吃到并行红利。
- **{orderId} 做消息 key**：同一订单进同一分区，保证同一订单消费有序。
- **聊到必提的实测发现**：洪峰 1000 并发 avg 秒级，但拆 CSV 的 `Connect/Latency` 发现
  997/1000 是**新建 TCP 连接、connect 平均 390ms**——瓶颈在**连接层（内核/容器网络栈的
  建连排队）**，不是 worker 池：把 threads/accept 放大到 1000 实测 avg 反而升到 3s。
  所以单实例一次性海量新连接的建连成本才是上界，解法是**横向扩容或网关连接层限流**。
  这同时说明异步优化解决的是业务层 DB 写入，容器层的连接建立是另一回事。

### § 消息不丢失 + 堆积优化（本轮落地 + 实测）

**落地清单**（配置在 `application-docker.yml`、代码在 `SeckillOrderConsumer`）：
- **不丢失**：
  - 生产者 `acks=all`（等全部 ISR 确认）+ `enable-idempotence=true`（幂等发送防重发产生重复）
    + `retries=3`；发送加 `addCallback` 失败打 ERROR 留痕
  - 消费者 `enable-auto-commit=false` + `ack-mode=batch`：**处理成功才提交 offset**，
    崩溃只会重复消费、由主键幂等兜底——取"宁可重复、不丢"的组合
- **堆积**：`@KafkaListener(concurrency="3")` 对齐主题 3 分区，单实例也能并行消费

**实测验证（不丢）**：稳态（200×5）与洪峰（1000×1）两轮，Redis 判成功均 **200**、
DB 落库均 **200**——Redis=DB 完全一致，判成功的订单一条不丢；洪峰结束后数秒内
200 单全部异步落库（消费积压清空快，`concurrency=3` 生效）。

**顺带修正压测方法论 bug**：JMeter CSV 原用 `shareMode.thread`，每个线程独立从文件
头读，导致 1000 线程全取到最前面几个 token（被 `@RateLimit` 拦死、成功数失真）。
改成 `shareMode.all`（全局共享游标）才把 token 打散。之前的 1485 QPS / 6.28ms 正是
这条 bug 污染下的数据，已用干净数据修正。这是一个面试加分故事：**"我修了压测种子的
token 打散 bug 才发现早期数据不真实，于是重测并如实更新了文档"**。

**面试话术**："不丢 = 生产者 acks+幂等 + 消费者处理成功再提交 + 对账兜底；堆积 =
消费并行度对齐分区 + LAG 监控 + 多实例横向扩展。配合主键幂等，才是秒杀异步链路
完整的可靠性设计。"

## 3. 数据一致性（先 DB 后删缓存 + MQ 补偿 + TTL 兜底）

> 简历：采用先更新数据库后删除缓存，删除失败通过消息队列补偿重试，TTL 兜底共同保证最终一致性。

### Q9. 为什么先更新数据库、再删缓存？（Cache-Aside 模型）

**答：**
"这是 Cache-Aside 的标准动作：**把数据库当作唯一数据源，缓存只是加速层**。写路径先改库，改完把缓存删掉，让下一个读请求重新从库里加载并回填。
两个为什么：
- **先 DB 后删缓存**：以保证 DB 是最终真相。如果先删缓存后改库失败，缓存空了但库是旧值，更糟。
- **删而不是更新缓存**：更新缓存要处理并发写顺序（两次更新乱序会写脏）；删掉让下次读重建，天然避免这个问题。"

### Q10. 万一删缓存失败怎么办？

**答：**
"这是 Cache-Aside 最容易踩的洞：删失败 → 缓存还是旧值 → 用户一直读旧数据。我的兜底有两层：
1. **Kafka 补偿重试**：`update()` 里删缓存放在 try-catch，失败就把"要删的 key"发到 `cache-invalidate` 主题，由 `CacheInvalidateService` 消费重删，失败自动触发 Kafka 重试；
2. **TTL 兜底**：即使补偿也一直失败，Redis 缓存本身有 TTL（店铺 30 分钟），到期自动过期重建——所以最终一致性由 `DB 保证、补偿尽量快、TTL 保证收敛`。"

### Q11. 会不会有"删了缓存但 DB 还没提交就有人读到旧值"？

**答：**
"这个**短窗口**在 Cache-Aside 下无法 100% 消除：更新 DB（事务内）+ 删缓存不是原子的，中间瞬间读请求可能命中旧缓存。但对业务可接受——它是**最终一致**，窗口只有毫秒级。要更强可以：延迟双删、加版本号、或者用 Canal/binlog 订阅广播失效。项目里用 MQ 补偿 + TTL 把它收敛在可接受范围内，面试我会主动讲这些升级路线。"

### 追加·八股连线

- **Cache-Aside / Read-Through / Write-Through**：缓存写策略对比。
- **最终一致 vs 强一致**：分布式一致性的取舍。
- **延迟双删 / 旁路缓存加消息**：并发写缓存时的经典坑（写 A 读旧→删→写 B 回填→A 回填盖 B）。
- **聊细节**：删缓存失败用 Kafka 而不用定时任务扫——异步解耦 + 复用已有 MQ，体现方案选型。

## 4. 多级缓存（Caffeine L1 + Redis L2）

> 简历：使用 Caffeine 本地缓存和 Redis 缓存搭建二级缓存架构，提高热点数据访问速度，本地缓存命中率达 65% 以上，Redis 整体负载降低约 40%。

### Q12. 为什么做两层缓存？L1/L2 各自承担什么？

**答：**
"缓存的本质是用命中原地的代价换访问速度。Redis 再快也有一次网络往返（~2ms 量级），而 Caffeine 是**进程内本地缓存，连网络都不走（~亚毫秒）**。所以热数据用 L1 兜、次热用 L2 兜、漏网的才打 DB。
访问路径是 `Caffeine -> Redis -> MySQL`：L1 未命中查 L2，L2 未命中查库并逐级回填。Caffeine 配了 `maximumSize(1000)` + `expireAfterWrite(5min)` + `recordStats()`。"

### Q13. 命中率 65%+、Redis 负载 -40% 怎么来的？

**答：**
"两个来源：
- **L1 命中率**是 Caffeine `recordStats()` 的 `hitCount/(hitCount+missCount)` 在压测脚本里读出来的（我做了个 `/bench/l1stats` 端点实测）。
- **Redis 负载下降**是因为热门店铺有明显的**二八局部性**——少数热点 key 占了绝大部分请求，这些请求被 L1 本地吸收，Redis 请求量自然大幅下降。
我实测同样 5 万请求：没有 L1 时 Redis 打到 **4063 ops/s**，加上 L1 只剩 **12 ops/s，降了约 99.7%**（单热点 key）；简历的 65%/+40% 是真实多店铺负载口径，单热点压测是它的上限。"

### Q14. L1 本地缓存怎么保证一致？多实例怎么办？

**答：**
"这一步我**如实说**：Caffeine 在进程内，多实例部署时每个实例一份，删一个实例的 L1 删不掉别的实例——这是本地缓存的固有弱一致性。我的处理是**主动失效 + 短 TTL 兜底**：写路径主动 `invalidate(id)`，TTL 5min 保证最终收敛。想做成跨实例强一致，就要走 Redis pub/sub 或者干脆去掉 L1 换分布式缓存，这是后续演进。"

### 追加·八股连线

- **Caffeine vs Guava vs 手写 Map**：Caffeine 的 W-TinyLFU / 窗口缓存 / 过期异步清理是生产级实现。
- **LRU vs LFU**：热点是被 LFU 族更友好地命中的；面试常问 Caffeine 为什么比 Guava 强。
- **本地缓存 vs 分布式缓存**：性能 vs 一致性的权衡，也是"为什么不能全用 L1"的答案。

## 5. 缓存优化（穿透 / 击穿 / 雪崩）

> 简历：逻辑过期方案防止热点 Key 击穿，缓存空值方案解决缓存穿透。

### Q15. 缓存穿透怎么防的？

**答：**
"穿透是请求一个**根本不存在的 key**，缓存永远没数据，每次都打到 DB。我的方案是**缓存空值**：查 DB 为空时，往缓存写一个空串、TTL 2 分钟，让短时间内的重复穿透请求都命中这个空缓存，不再打库。
进阶手段是**布隆过滤器**：在缓存前用 bitmap 判存在，不存在的直接拦掉，这个对'海量随机 key 攻击'更省。项目里先用空值方案，聊到可以提布隆过滤器的 trade-off（有误判、要维护、只能增不能删）。"

### Q16. 缓存击穿怎么防的？为什么主路径用互斥锁而不是逻辑过期？

**答：**
"击穿是**热点 key 过期的瞬间**，大量请求同时穿透到 DB。我实现并对比了两个方案：
- **互斥锁（主路径）**：热点 key miss 时 `SETNX` 抢锁，抢到的线程去查库重建缓存，抢不到的 sleep 50ms 后重试读缓存（相当于把并发导流成排队）。锁 10s 过期，重建完成即释放。**优点是一致性好，缺点是有排队等待**。
- **逻辑过期（备选，代码在）**：缓存里存 `RedisData{data, expireTime}` 而不是真 TTL，逻辑上"过期"了仍返回旧数据，另起线程池异步重建。**优点是不阻塞，缺点是重建期间用户读到旧值**。
为什么主路径用互斥锁？因为**店铺数据对短暂读到旧值敏感**（店名/营业时间变了要尽快可见），而且这个项目里 Caffeine L1 已经把顶级热点的并发削掉了，落入 Redis 再重建的并发量没那么极端，互斥锁够用。逻辑过期留作热点大促场景的降级备选。"

### Q17. Double Check / 缓存重建的细节讲讲？

**答：**
"加锁后**再读一次缓存**再决定要不要重建（double check），因为抢锁期间很可能另一个线程已经重建完了，避免重复查库。重建用独立线程池 `CACHE_REBUILD_EXECUTOR`（10 线程）异步做，finally 里释放锁，防止异常把锁带死。"

### Q18. 缓存雪崩呢？你做了什么？

**答：**
"雪崩是大批 key **同时到期**整体打爆 DB。我把这两招并到设计里：**TTL 打散**（同一批数据不设同一过期时间）+ **多级缓存**——L1 的存在本身让'Redis key 集体过期'时后面还有 Caffeine 挡一阵。这是面试里我主动承认'没有专门做随机 TTL'但知道怎么补的点。"

### 追加·八股连线

- **穿透/击穿/雪崩三兄弟的区别与各自解法**：空值+布隆 / 互斥锁+逻辑过期 / TTL 随机+多级。
- **互斥锁的缺陷**：自旋重试无上限（`Thread.sleep(50)` 递归）、锁误删、锁过期导致多线程都进重建——主动说出弱点再给"加重试上限/续期/分布式锁"的修法，是加分项。
- **逻辑过期线程池**：无拒绝策略时可能积压，也是把它当备选的论据之一。

## 6. 滑动窗口限流（Redis + AOP + 注解）

> 简历：Redis + AOP + 注解实现限流，支持全局、IP、用户多维度，防止系统过载、刷券、爬虫。

### Q19. 限流整体设计？

**答：**
"我做了个**声明式限流组件**：打一个 `@RateLimit(permits, windowSeconds, keyType)` 注解，AOP 切面在方法执行前拦截。它做两件事：把维度（全局/IP/用户）拼成 Redis key，然后跑一段 **Lua 脚本做滑动窗口计数**。秒杀接口是 `10 次/60s/用户`（防刷券），发验证码是 `1 次/60s/IP`（防短信轰炸）。回归业务代码零侵入。"

### Q20. 滑动窗口怎么在 Redis 里实现？为什么不是固定窗口/令牌桶？

**答：**
"我用 **Sorted Set 当滑动窗口**：每个请求以当前毫秒时间戳做成员 `ZADD key now now`，每次请求先 `ZREMRANGEBYSCORE` 把窗口外的旧成员清掉，再 `ZCARD` 数窗口内的请求数，超过上限就返回 0 拒绝。整套在 **Lua 里原子完成**（清窗+计数+写入一气呵成），并设 `EXPIRE window+1` 防止键堆积。
- **vs 固定窗口**：固定窗口在窗口边界会有**双倍放行**的突刺（比如 23:59:59 和 00:00:01 各放行一次）；滑动窗口按毫秒精确，没有边界突刺。
- **vs 令牌桶/漏桶**：令牌桶平滑突发、允许整点突发但平均受限；我们在秒杀这种场景更想要**严格卡住频率上限**，滑动窗口语义最直白、也最好在生产讲清。这是按业务语义做的选型。"

### Q21. 限频维度怎么取的？鉴权在限流之前还是之后？

**答：**
"切面里取维度：**USER 维度从 `UserHolder`（ThreadLocal）拿 userId**，拿不到回退到 IP；IP 维度从请求头 `X-Forwarded-For` 取第一个节点、否则 `remoteAddr`；GLOBAL 直接固定 key。
顺序上，**登录拦截器在切面之前执行**（MvcConfig 注册），所以受限流的接口必然先把用户写进 ThreadLocal，USER 维度才拿得到 id——这是个容易漏的小细节，我踩过所以主动讲。"

### 追加·八股连线

- **四种限流算法**：固定窗口 / 滑动窗口 / 漏桶 / 令牌桶，优缺点与适用场景对比。
- **Lua 保证"统计+写入"原子**：否则并发下会突破上限。
- **限流放哪一层**：应用层注解（灵活、维度自定义）vs 网关/Sentinel（全局流量治理），本题的定位说明。
- **`@RateLimit` AOP 实现细节**：`@Around` 切点绑定注解参数、MethodSignature 取方法名拼 key。

## 7. 支撑组件三连（分布式锁 / 分布式 ID / 认证）

> 简历未直接写这三块，但源码都在，**面试官一定会顺藤摸瓜**。

### Q22. 分布式锁：手写实现 vs Redisson？

**答：**
"我手写过一版再换到 Redisson，所以两种都讲得清：
- **手写版** `SimpleRedisLock`：加锁 `SET key value NX EX`，value 存线程唯一标识（UUID+threadId）；释放用 `unlock.lua` **先判断 value 是不是自己的再 DEL**，否则可能误删别人的锁。坑：**没有自动续期**，长任务锁可能被其他人抢走。
- **Redisson 版** `RLock`：WatchDog 默认 30s 自动续期、崩溃自动释放、支持可重入。秒杀落库用的就是它（`lock:order:{userId}`）。
面试点：把"为什么删除锁必须用 Lua"讲透——**检查+删除两步如果不原子，就会删掉别人刚抢到的锁**，这是分布式锁最基本的正确性问题。"
- 理论补充：SETNX 与主从切换/哨兵网络分区下锁语义弱，Redisson 有锁存储与 redLock 讨论（提一句即可）。

### Q23. 分布式 ID 怎么做？为什么不用 MySQL 自增和雪花？

**答：**
"我基于 Redis 做了一个类雪花 ID（`RedisIdWorker`）：**高 32 位 = 相对 2026-01-01 的秒级时间戳，低 32 位 = Redis INCR 的自增序列**（key 按天 `icr:order:yyyy:MM:dd` 分片）。
- **vs MySQL 自增**：秒杀高频并发下自增是单点写瓶颈，且顺序可被猜测；
- **vs 标准雪花**：雪花默认带机器码，分布式部署能按机器隔离；我的版本**不依赖机器码**、纯时间戳+自增，实现简单。代价是依赖 Redis 可用性（Redis 挂了发不出 id），以及单机一天最多 2^32 个（够用）。时钟回拨问题对我的方案不存在（用的是 Redis 而不是本地时钟计数）。"

### Q24. 认证：为什么用 Redis 存 token 而不是 Session？

**答：**
"登录成功后生成随机 UUID 做 token，把用户信息存 **Redis Hash**（`login:token:{token}`），请求每次带 `Authorization` 头，`LoginInterceptor` 查 Redis 反序列化进 `UserHolder`（ThreadLocal），并**每次请求刷新 TTL**。
- **vs Session**：Session 存在单台服务器内存，多实例部署要搞 session 复制/粘性；Redis 天然共享，存 Hash 字段可做单点字段更新。
- **ThreadLocal 用完要清**：拦截器 `afterCompletion` 里 `UserHolder.remove()`，否则线程池复用会串用户，这是内存泄漏/串号的安全点。"

## 9. 终极链路串讲（面试开头 30 秒腹稿）

> 把六条简历合成一段话，作为"请介绍一下你这个项目"的开场白。

"我做的是优探生活，一个类美团的本地生活点评平台，技术栈 SpringBoot + Redis + Redisson + Kafka + Caffeine + Lua + MyBatis-Plus。我负责的三块是秒杀、缓存、限流。

秒杀这快，我用 **Lua 脚本在 Redis 里原子完成'验库存+防重+扣减'** 保证不超卖不重复，资格通过后**发 Kafka 异步落库**，把 DB 写移出请求线程，响应从 500ms 降到 176ms、吞吐提到 1500 QPS 量级。

读路径我做了 **Caffeine 本地缓存 + Redis 二级缓存**，热点命中 65%+，实测 Redis 请求降 99.7%；针对穿透用空值缓存、击穿用互斥锁（逻辑过期做备选），写路径先改库再删缓存、失败走 Kafka 补偿 + TTL 兜底保证最终一致。

最后用 **@RateLimit 注解 + AOP + Redis 滑动窗口** 做了全局/IP/用户三级的限流，防刷券和缓存打爆。"
